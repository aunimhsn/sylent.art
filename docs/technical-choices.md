# Technical choices

The technical choices of the [roadmap](../roadmap.md), with their reasons and the alternatives rejected. Chosen with the owner on 2026-10-27 (step 2) and applied by the project skeleton of step 6 (2026-10-28).

## Stack

| Topic | Choice | Reason |
|---|---|---|
| Hosting | GitHub Pages, custom domain `sylent.art` | Free for a public repository, no server to maintain, HTTPS included. The site must work without a server. |
| Static site generator | [Astro](https://astro.build/) 7, static output | Built-in redirects, validated content collections, image optimization and zero JavaScript by default (see [Astro](#astro)). Its syntax (HTML, CSS, a little JavaScript, close to Vue) is familiar to the owner, who edits the site too. |
| Runtime and packages | Node.js 24 LTS, npm (`package-lock.json`) | Astro 7 needs Node.js 22.23.4 or later. The version is pinned in `.nvmrc` and in `engines` of `package.json`, and CI uses the same one. npm is already installed: no other package manager to learn. |
| Styles | Native CSS, design tokens as CSS custom properties | See [Styles](#styles). Tailwind CSS may come later. |
| Content | Markdown files in Astro content collections; interface texts in a French translation file | The French content stays out of the layout and components, so that a translation can be added later (see [Content](#content)). |
| Contact form | Formspree, free plan | No server needed, 50 submissions a month (far above the expected volume), spam filter. Web3Forms rejected: its documentation contradicts itself on storage. See [external-services.md](external-services.md). |
| Audience measurement | GoatCounter | No cookie, so no consent banner; data hosted in the European Union; free for a small business. Google Analytics rejected: consent banner required. See [external-services.md](external-services.md). |
| Formatter | Prettier, with `prettier-plugin-astro` | The usual formatter for Astro, CSS, JavaScript, JSON, YAML and the Markdown content: one tool for every file of the site. The project documentation (`*.md` at the root, `docs/`, `.claude/`) is left out (`.prettierignore`): Prettier would pad every table to its widest cell, which makes the long tables unreadable in an editor. |
| Linter | ESLint with `typescript-eslint`, `eslint-plugin-astro` and its strict accessibility rules (`jsx-a11y-strict`, with `eslint-plugin-jsx-a11y-x`); Stylelint with `stylelint-config-standard` and `stylelint-config-html` (the `<style>` blocks of the components); `astro check` | ESLint catches errors and missing accessibility attributes (`alt`, labels) in the templates, Stylelint invalid or duplicate CSS, `astro check` type errors and wrong component props. `eslint-plugin-jsx-a11y-x` is the maintained fork that `eslint-plugin-astro` supports: the original `eslint-plugin-jsx-a11y` has had no release since 2024 and refuses ESLint 10. Stylelint keeps the colors in six-digit hex (`color-hex-length: long`), as `docs/branding.md` writes them. |
| Link check | linkinator on the built site, plus a script for the former URLs | See [Link check](#link-check). |
| Phone width check | A script that loads every page in the Chromium of [Playwright](https://playwright.dev/), as on a phone | See [Phone width check](#phone-width-check). |
| Deployment | GitHub Actions workflow (`.github/workflows/deploy.yml`) on every push to `main`, with `withastro/action` and `actions/deploy-pages` | A merged pull request is deployed without a manual step, using the actions documented by Astro and GitHub. See [Deployment](#deployment). |
| Checks in CI | GitHub Actions workflow (`.github/workflows/ci.yml`) on every pull request | Runs the same commands as before a commit: build, format, lint, links, phone width. |

## Astro

- **URLs with a final slash**: Astro writes each page as a folder with an `index.html` (`build.format: "directory"`, its default), and GitHub Pages serves `a-propos/index.html` at `/a-propos/` and redirects `/a-propos` to it (301): the former URLs keep working and keep their ranking. The links and canonical URLs end with a slash, and `trailingSlash: "always"` makes the development server behave the same way. Rejected: one `about.html` file per page, which GitHub Pages serves at `/about` without a redirect, but whose behavior is not documented when a folder of the same name exists (`domaines.html` beside `domaines/`).
- **Redirects**: in a static build, Astro's `redirects` option writes, for each former URL, a page with a canonical link and an immediate `<meta http-equiv="refresh">`, which is what `specs.md` asks for since GitHub Pages has no server-side redirects. Astro doesn't add the base path to their destination: `astro.config.mjs` adds it. The redirects of `/courses/<id>` are generated by `src/pages/courses/[id].astro` (`Astro.redirect`, which writes the same page) from the `formerId` of each module, so a former URL cannot be forgotten; the others, `/courses`, `/about` and `/policy` toward their French paths and `/articles`, `/articles/1`, `/articles/2` to the home page since the site has no articles, are written in `astro.config.mjs`.
- **Redirect pages in French**: `experimental.redirectPage` (Astro 7.4, still experimental on 2026-10-30, chosen with the owner) writes each redirect, those of `redirects` and of `Astro.redirect` alike, with `src/pages/3xx.astro` instead of Astro's page in English: a black page « Cette page a changé d’adresse », with the same immediate refresh, canonical link and `noindex`, without the fonts and scripts of the site. Astro also builds the template itself as `/3xx.html`, without a redirect to fill it: a hook of `astro.config.mjs` removes it. If the option changes or disappears, Astro falls back to its own page, and the redirects keep working.
- **Sitemap and `robots.txt`**: `scripts/sitemap.mjs`, a small integration of `astro.config.mjs`, writes `sitemap.xml` once the site is built, from the canonical link of every built page that points to itself: the redirect pages, whose canonical link points to their target, and the not-found page, which has none (`noindex`), are left out by construction, and a new page is listed without changing the script. `src/pages/robots.txt.ts` allows every page and gives the address of the sitemap. Rejected: `@astrojs/sitemap`, a dependency whose filter would have to list every redirect, the `Astro.redirect` pages of the former courses and of the formations of a single module included.
- **Not-found page**: `src/pages/404.astro`, written as `404.html`, which GitHub Pages serves for every path without a page, with `noindex` and no canonical link.
- **French paths** (see `specs.md`, URLs and redirects): `/formations/<formation>/<module>/` for a module, independent of the domains (decided by the owner on 2026-10-30, at step 13, replacing the tree `/domaines/<domain>/modules/<module>/` of 2026-10-29, which was only on the preview and got no redirect), `/formations/<formation>/` for a formation, `/domaines/<domain>/` for a domain, `/a-propos/`, `/confidentialite/`, `/mentions-legales/`. The module page is `src/pages/formations/[collection]/[module].astro`, the formation page `src/pages/formations/[collection]/index.astro` (a redirect to its module for a formation of a single module), the domain page `src/pages/domaines/[domain]/index.astro`, their paths given by `modulePath`, `formationPath` and `domainPath` in `src/lib/offers.ts`. `/formations/` shows one card per domain, as the home page; `/domaines/` and `/courses/` redirect to it.
- **Content collections**: each domain, formation and module is a Markdown file whose front matter is validated by a schema at build time (title, summary, domains, `formerId`, scene…). A missing field, an unknown scene, a duplicate order or former id, or a domain whose list of formations doesn't match its modules (checked across files by `src/lib/offers.ts`) fails the build instead of publishing a broken page. A formation is a **collection** in the code (`src/content/collections/`, the `Collection` and `Formation` types), as `specs.md` says; the Astro word « collection » names the three folders as well.
- **Images**: the `astro:assets` `<Image>` component converts the images to WebP at the size they are shown and sets their width and height, which avoids layout shifts.
- **JavaScript**: the approved mock-up moves (section headings, reveals, the 3D cube and covers, the orange fluid of the grids; see [docs/branding.md](branding.md#motion)), so the site bundles [GSAP](https://gsap.com/) (with ScrollTrigger and SplitText) and, from step 7b, [Three.js](https://threejs.org/), installed with npm: Astro bundles the `<script>` of the components and the modules of `src/scripts/` into a few files served by the site itself, without a CDN. The content never depends on them: the pages are complete HTML, the elements an animation reveals show after 4 s if the scripts don't start, and nothing moves when the visitor asked their system to reduce motion (`data-motion`, set in the `<head>` before the first paint; `?motion=off` does the same, for checks and screenshots). The contact form is sent with `fetch` so that the visitor stays on the page, and still posts to Formspree without JavaScript. Chosen on 2026-10-28 (step 7), replacing « no JavaScript but the form and GoatCounter », written before the mock-up.
- **Size of Three.js**: the cube and the covers bundle Three.js as one module of about 540 kB minified (135 kB compressed), which Vite can't split; `chunkSizeWarningLimit` is set to 600 kB in `astro.config.mjs`, so that the build stays without warnings while any other large chunk still shows. The module is loaded after the page is shown (`type="module"`); the cube is imported dynamically, so that the intro of the hero, which shows the headline, doesn't wait for it.
- **Intro of the hero**: its elements stay hidden until `src/scripts/hero-intro.ts` sets `data-intro-started`, or until 4 s have passed (an inline timer of the hero), as the reveals do with `is-js`.
- **Licenses of the scripts**: Three.js is under the MIT license. GSAP is free for commercial use under its own [standard license](https://gsap.com/standard-license), which is not an open source license: it forbids only using GSAP in a tool that competes with Webflow, its owner, which the site doesn't. Noted with the owner on 2026-10-28.
- **`CNAME`**: kept in `public/CNAME`, which Astro copies as is to the root of the published site.
- **Fonts**: Astro's Fonts API (`fonts` in `astro.config.mjs`, `<Font />` in the layout) downloads Manrope and Anaheim (SIL Open Font License) from Google Fonts at build time and serves them from the site itself, with a fallback font adjusted to their metrics so that the text doesn't move when they load. Only what the site uses is downloaded: the Latin characters, Manrope from 600 to 800 and Anaheim 500, both preloaded (the Roman numerals of the pedagogy were in Bodoni Moda until 2026-10-29). They replace the `public/fonts/` folder first planned: no font file to download and update by hand.
- Rejected:
  - **Eleventy**: just as capable for a static site, but the redirects, image conversion and content validation have to be assembled from plugins and configuration by hand.
  - **Hugo**: one fast binary, but its Go template language is harder to read and to edit for the owner.
  - **Hand-written HTML**: the header, navigation and footer would be copied in every page, and nothing would check the content or the redirects.
  - **Laravel or Vue (as an application)**: known to the owner, but they need a server or ship a JavaScript application, while the site is a handful of static pages.

## Deployment

- `.github/workflows/deploy.yml` follows the [Astro guide](https://docs.astro.build/en/guides/deploy/github/): `withastro/action` installs, builds and uploads `dist/`, then `actions/deploy-pages` publishes it. In the repository's **Settings → Pages**, the source is **GitHub Actions**.
- **Until the launch**, the owner checks the site at https://aunimhsn.github.io/sylent.art/, a project site under the `/sylent.art` base path. The workflow sets `SITE_URL` and `BASE_PATH`, read by `astro.config.mjs`; without them (development server, checks, CI) the site is built for `https://sylent.art` at the root. So every internal link and asset path must go through the base: Astro prefixes the files it builds (styles, fonts, images), and the links written in the templates start with `import.meta.env.BASE_URL`. `npm run check:base` builds this preview into `dist-base/sylent.art/` and checks its links, so a link without the base fails the checks. Under a base, the layout adds `noindex`, so that search engines don't index the preview beside the former site.
- **At the launch** (step 14), once the DNS of `sylent.art` points to GitHub Pages: remove the two variables from `deploy.yml` and the `check:base` script, set the custom domain in the Pages settings and enforce HTTPS. A workflow with `actions/deploy-pages` ignores the `CNAME` file for the domain; `public/CNAME` is kept as `CLAUDE.md` asks.
- `.github/workflows/ci.yml` runs `npm run check` on every pull request, with the Node.js version of `.nvmrc`. A ruleset on `main` (created on 2026-10-28) requires a pull request, merged by squash only, whose `check` job passes, and forbids force pushes and deleting the branch; the owner, as administrator, can bypass it in an emergency.
- Only the `deploy` job may write to GitHub Pages (`pages: write`, `id-token: write`); the build job, which runs the dependencies, only reads the repository. The actions are referenced by major version, as in the guides; pinning them by commit and Dependabot are left for after the launch.

## Styles

- **Design tokens** are the named values of the visual design: `--signal: #d3450e`, `--space-4: 16px`, `--size-card-title: 21px`. They were written in step 5, in [docs/branding.md](branding.md).
- In native CSS, they are CSS custom properties declared once in `src/styles/tokens.css`, and every component uses them (`color: var(--signal)`). Changing the main color then means changing one line.
- This matches the mock-up: its components use only these variables. The `:root` block of `docs/mockups/shared/site.css` becomes `tokens.css` as is, and the CSS of the mock-up's components can be copied into the Astro components without translation.
- The **breakpoints** (640, 760, 900 and 1100 px) can't be CSS variables, since a media query doesn't read them: they are written as numbers in the media queries, and listed in [docs/branding.md](branding.md#layout-and-shapes).
- Component styles live in the `<style>` block of each Astro component, which Astro scopes to that component: a class name in one component cannot break another. A component styles the inside of a child component (an SVG logo, an icon) with `:global(...)` inside one of its own selectors, which Stylelint accepts.
- The classes shared by every page (`.wrap`, `.section`, `.button`, `.lead`, `.motto`, `.glass`, `.reveal`, `.visually-hidden`…) are in `src/styles/global.css`. They are those of the mock-up without its `app-` prefix, which only kept the mock-up's names apart: a style copied from the mock-up drops the prefix.
- **Grid textures** are written once, in `global.css`: `.grid-lines` draws the lines of a grid (the footer), `.grid-texture` a grid behind a block (the heroes of the home, about, domain and module pages) under a mask given by the block (`--grid-mask`), with the layer of its orange fluid at the same place, and `.is-page-top` stretches it to the top of the page and the width of the window (the domains page, the text pages, the contact page). A block that holds one only sets its mask or its cell (`--grid-cell`).
- **Tailwind CSS** (liked by the owner for quick changes) is not used for now. If the project moves to it later, Tailwind 4 declares its theme with CSS variables (`@theme`), so the same tokens carry over; record that change here.

## Content

- `src/content/domains/<slug>.md`: one file per domain, named after its slug (see `specs.md`): its title, its `ghost` (the one word behind the title of a module alone in its formation, « Web »), summary, order, scene, `isNew`, an optional `note` shown on the pages of its modules, and its `collections`, the formations of its page in their order: every formation with a module filed under the domain, drafts included, and no other (a formation may be in another order in another domain, so the order lives in the domain).
- `src/content/collections/<slug>.md`: one file per formation, named after its slug, which starts the URL of its modules: its title, and its `summary`, required once it has two published modules (its page). The cover of a formation card is the scene of its first module.
- `src/content/modules/<collection>/<slug>.md`: one file per module, in the folder of its formation, named after its slug, which ends its URL (`/formations/<collection>/<slug>/`); a slug is unique within its formation only (`fondamentaux`). The front matter gives its `domains` (the first one first), its `order` in the formation (the advised order), its duration in days (kept for the quotes, shown nowhere), summary, scene, `framework: true` for a framework, `formerId` for a former course, `draft: true` to keep it out of the site until the owner publishes it (its former URL then leads to the page of its formation, or of its first domain when the formation has no page), and its audience, level, prerequisites, objectives and program; the Markdown text is its presentation. The module alone in its formation is named after it (« UML »), and shown by the name of the formation. The schemas are in `src/content.config.ts`, the scene names in `src/lib/scenes.ts`, the checks across files in `src/lib/offers.ts`.
- `src/content/courses.json`: the texts of the formations page, the domain, formation and module pages (labels, notes, calls to action).
- `src/i18n/fr.json`: the interface texts (navigation, footer, buttons, form labels and messages), so that no French text is hard-coded in a component. A script that shows a text (« Copiée », the label of the menu button) reads it from a data attribute that the component fills from this file.
- `src/data/contact.json`: the public contact details (email, phone, LinkedIn, GitHub), the SIRET and the NDA, shared by the footer, the contact page, the about page and the legal notice.
- `src/lib/url.ts`: every internal link goes through `href("/a-propos/")`, which adds the base path of the github.io preview (see [Deployment](#deployment)).
- Other French page texts are data files in `src/content/`: `about.json` (the about page), `legal.json` and `policy.json` (the legal notice and the privacy policy: title, lead, date of the last update and sections of facts, cards and paragraphs, shown by `src/components/text-page.astro`).
- **Links and stressed text in a content file**: a text of the legal notice, the privacy policy or the about page may hold a link, `[politique de confidentialité](/confidentialite/)`, and stressed text, `**Cet enregistrement…**`, as in Markdown; `src/lib/rich-text.ts` reads them and `src/components/rich-text.astro` shows them, a link to a page of the site through the base path, a link to another site in a new tab. `{email}`, `{siret}`, `{nda}` and the other keys of `src/data/contact.json`, and the fixed sentences of `details` in `src/i18n/fr.json` (`{ndaNotice}`, the sentence that always follows the NDA), are replaced by their value, so that each one is written once. A link must start with `/`, `https://`, `mailto:` or `tel:`: anything else, as an unknown key, fails the build. The dates are written in full by `src/lib/dates.ts` (« 1er novembre 2026 »), in the language of `fr.json`. The texts stay plain text, escaped by Astro, without a Markdown dependency. Rejected: Markdown files with HTML for the facts, which would write the contact details again.
- `src/content/home.json`: the texts of the home page (hero, faces of the cube, audiences, headings, cycle of a lesson); a face of the cube that shows a key figure refers to it by its `id` in `pedagogy.json`, and the lead of the domains counts the published domains (« Sept domaines »), so that each fact is written once; `src/content/pedagogy.json`: the steps of the pedagogy and the key figures, shared by the home and about pages. They are imported as JSON, like `fr.json`, since they are not collections of entries.
- `src/content/not-found.json` and `src/content/redirect.json`: the texts of the not-found page and of the redirect pages.
- `src/data/partners.json`: the partners, the file name of their logo in `src/assets/partners/` (white SVG, served as is) and its scale.
- The site is edited by the owner and Claude Code only, in the repository: no content management system.

## Link check

- **linkinator** serves the built site (`dist/`) as a static host would, so `/a-propos` resolves to `a-propos/index.html` as on GitHub Pages, and follows every internal link of every page. External links are skipped in the regular check, so that a slow third-party site doesn't break the CI.
- **`scripts/check-former-urls.mjs`** checks that every former URL (`/`, `/courses`, `/courses/1` to `/courses/12`, `/articles`, `/articles/1`, `/articles/2`, `/about`, `/contact`, `/policy`) exists in `dist/`, that each redirect points to the path `specs.md` gives it, written in the script, and that this page, and its anchor if any, exists (a redirect whose target it can't read fails); `npm run check:base` runs it on the github.io preview too, with its folder and its base, and that the dropped URLs (`/creations`, `/register`, `/login`) are not built. The URLs whose page a later step builds go in its `pending` list, with the step: each step removes its own (the check fails if a pending URL is built). The list is empty since step 9b. It also checks the redirects of the site, which no page links to and linkinator can't see: `/domaines/` leads to the formations page, and the address of each formation of a single module (`/formations/uml/`) to its module.
- linkinator's options are in `linkinator.config.json`: it follows the internal links, checks the URLs of the CSS (fonts) and the anchors (`#…`), and skips every address that isn't its local server.
- **Links to pages still to build**: from step 7, the header and the footer linked to pages built by later steps; linkinator skipped them through a second pattern of `skip` in `linkinator.config.json`, removed in step 9b once every page of the first release existed. A link to a page not built yet goes there again, until its step.
- Rejected: **lychee**, faster, but a Rust binary that the owner would install apart from npm; linkinator runs from `npm ci` locally and in CI alike.

## Phone width check

- **Why**: on 2026-10-29 the owner saw a black band on the right of the home page on an Android phone. The large faded words of the headings ran past the right edge of the screen; `overflow-x: hidden` on the body hid them on a computer, but the browser of the phone (Chrome on Android, or one built on Chromium) still widened the page to show them (up to 686 px for a 360 px screen on the module pages), and the grids, as wide as the screen, left a black band beside them. linkinator and the build can't see it: only a browser that lays the page out can.
- **The rule**: `main` clips what runs past its sides (`overflow-x: clip` in `src/styles/global.css`, which makes no scroll container, so the sticky blocks keep working). Anything that may run past the edge of the screen, as a large faded word, goes inside `main`, which `src/layouts/site-layout.astro` gives every page: the not-found page of step 14 too, with its large « 404 ».
- **`scripts/check-overflow.mjs`** serves `dist/` as GitHub Pages would, loads every page (the not-found page `404.html` included, the redirect pages left out) in the Chromium of Playwright as on a phone (`isMobile`, 320, 360 and 412 px wide), then on a computer (1024 and 1440 px, where « Développement web » broke mid-word, seen by the owner on 2026-10-29), scrolls it to the bottom by instant jumps, since the faded words slide with the scroll (the smooth scrolling of the site would stop each jump short), and fails if the page got wider than the screen, or if a large white title of a module, domain or section heading takes more than one line (asked by the owner on 2026-10-29; `docs/branding.md`, Type). A page that fails to load or whose scripts throw is reported with the others. Four tabs at once: about 35 seconds for the site.
- **Playwright** (`playwright`, the library without its test runner, a development dependency only) is the usual way to drive a browser from Node.js, maintained by Microsoft. Its Chromium is downloaded apart, headless only (`--only-shell`, without the 400 MB of the full browser): once with `npx playwright install --only-shell chromium` locally, at every run with `npx playwright install --with-deps --only-shell chromium` in CI (with the system libraries of Ubuntu; Playwright advises against caching the browser). Chromium rather than Firefox: the bug showed on Android, whose browsers are mostly built on Chromium, and Playwright emulates their mobile layout. Rejected: Puppeteer, as able for this check, but Playwright also drives Firefox and WebKit (Safari), should a check need them later; a Firefox driven by hand over WebDriver BiDi (the tool of the mock-up screenshots), which needs a Firefox installed apart and doesn't lay out a page as Chrome on Android does.

## Size and left edge of the large titles

- **Why**: the owner asked on 2026-10-30 that each module and domain title be as large as the display size allows on one line, from its own width (« Laravel » 44 px on a phone instead of 34 px), and that the large titles and faded words start from the ink of their first letter, not its side bearing (`docs/branding.md`, Typography). The mock-up measures them in the page with JavaScript (`docs/mockups/shared/formations.js`); the site computes them at build time, so that the page needs no script and doesn't move once the font arrives.
- **`scripts/font-metrics.mjs`** measures Manrope 800 in the Chromium of Playwright, from the file the site serves (`.astro/fonts/`, downloaded by `npm run build`): the advance of each character a title may hold, the side bearing on the left of its ink (read on the pixels of the drawn letter: `measureText` rounds it to 1/64 em; the values match the font file read with fontTools), and the kerning of each pair, which moves a title by up to 0.18 em (« JAVASCRIPT »). It measures with a letter spacing, then takes it off, as the titles are tracked in the page: a letter spacing turns the ligatures off (« ff » is 6 % wider than its ligature). A character the served file lacks (« Ÿ », outside its latin subset) is left out, and so is the narrow no-break space, which Chromium doesn't track. It writes them to `src/data/manrope-800.json` (31 KB, read only at build time), committed; run it again (`npm run build && npm run fonts:metrics`) when the font or the characters of the titles change. A title with a character it didn't measure fails the build. `npm run check:overflow` first checks that the measured file is the one the build serves (`dist/_astro/fonts/`, after the name of the file): Google Fonts may update Manrope, and the check then asks to run the script again.
- **`src/lib/title-metrics.ts`** adds them up: the width of a text in em with its letter spacing, read from `src/styles/tokens.css` (`--tracking-title`, `--tracking-ghost`), kerning included (`--title-em` and `--ghost-em` of `src/components/page-hero.astro`), and the side bearing of its first letter (`--bearing`), 0.01 em more for a round capital. The width of a title takes 5 % more: Chromium on Linux sets each letter on a whole pixel, which makes a title up to 4.4 % wider than measured at 38 px (measured on every title from 30 to 92 px); `npm run check:overflow` fails on a title on two lines.
- Rejected: reading the font with a JavaScript library at build time (`fontkitten`, already installed by Astro, can't read the character map of this file, and applies no kerning); fontTools, in Python, which CI would install apart; measuring in the page, as the mock-up does.

## Commands

Run `npm ci` first. They are also in the `scripts` of `package.json`.

| Command | What it does |
|---|---|
| `npm run dev` | Local development server, reloads on every change (`http://localhost:4321`). |
| `npm run build` | Production build to `dist/`; must finish without errors or warnings. |
| `npm run preview` | Serves the production build of `dist/` locally. |
| `npm run format` | Formats every file with Prettier. |
| `npm run format:check` | Checks the formatting without changing files (used in CI). |
| `npm run lint` | `astro check`, ESLint and Stylelint. |
| `npm run check:links` | Checks the internal links, the former URLs and the redirects of the tree on `dist/` (run after `npm run build`). |
| `npm run check:overflow` | Checks that no page is wider than a phone screen and that the large titles hold on one line, on a phone and on a computer, in the Chromium of Playwright (run after `npm run build`; install the browser once with `npx playwright install --only-shell chromium`). |
| `npm run fonts:metrics` | Measures Manrope 800 for the size and left edge of the large titles into `src/data/manrope-800.json` (run after `npm run build`, when the font or the characters of the titles change). |
| `npm run check:base` | Builds the github.io preview (`/sylent.art` base) into `dist-base/` and checks its links; removed at the launch. |
| `npm run check` | Everything run before a commit and in CI: format check, lint, build, links, phone width and titles, links of the preview. |

## Exceptions to the naming conventions

Imposed by Astro or the tools, everything else in kebab-case:

- `src/pages/404.astro` and `src/pages/3xx.astro`: the names Astro gives the not-found page and the redirect page; `src/pages/robots.txt.ts`, named after the file it writes.
- Dynamic route files and folders use brackets: `src/pages/domaines/[domain]/index.astro`, `src/pages/formations/[collection]/index.astro`, `src/pages/formations/[collection]/[module].astro`, `src/pages/courses/[id].astro`.
- Configuration files keep the names the tools look for: `astro.config.mjs`, `src/content.config.ts`, `eslint.config.js`, `.prettierrc`, `.prettierignore`, `.stylelintrc.json`, `linkinator.config.json`, `.nvmrc`, `tsconfig.json`, `.vscode/extensions.json` (the VS Code extensions of Astro, Prettier, ESLint and Stylelint, proposed when the folder is opened).
- Component files stay in kebab-case (`src/components/site-header.astro`), although the Astro documentation names them in PascalCase; they are imported under a PascalCase name (`import SiteHeader from ...`), as Astro requires for components in templates.
